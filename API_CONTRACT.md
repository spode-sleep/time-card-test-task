# Данные и контракт API графика смен

Контракт подготовлен на этапе 2 и реализован на этапе 3. Служебный маршрут `/api/health` проверяет доступность PostgreSQL.

Общие TypeScript-типы находятся в `shared/src/schedule.ts`, схема БД — в `backend/prisma/schema.prisma`.

## Форматы данных

| Значение | Формат |
| --- | --- |
| Идентификаторы сотрудников, шаблонов, назначений, публикаций и запросов | UUID |
| Дата ячейки | `YYYY-MM-DD`, существующая календарная дата с четырёхзначным годом |
| Время смены | `HH:mm`, диапазон от `00:00` до `23:59` |
| Переход через полночь | `endDayOffset` со значением `0` или `1` |
| Временная метка публикации | ISO 8601 в UTC, например `2026-11-19T15:00:00.000Z` |
| Ревизия | Целое неотрицательное число в диапазоне PostgreSQL `integer` |
| Цвет карточки | `#RRGGBB` |

Строковые типы даты и времени описывают формат передачи. Проверка формата и существования даты выполняется сервером при реализации API.

Расписание единое, запись `Schedule` имеет идентификатор `1`. Миграция создаёт её с ревизией `0` и часовым поясом `Europe/Moscow`.

Дата назначения обозначает день начала смены в часовом поясе расписания. В PostgreSQL хранится тип `DATE`. При работе через Prisma строка преобразуется в `Date` на полночь UTC и обратно только по UTC-компонентам. Часовой пояс браузера сохраняет исходную календарную дату.

Время в БД хранится целым числом минут от начала суток. API переводит его в `HH:mm`. Длительность в минутах вычисляется по формуле `endMinute + endDayOffset * 1440 - startMinute`.

- Для смены в пределах суток окончание позже начала и `endDayOffset` равен `0`.
- Для ночной смены окончание раньше начала и `endDayOffset` равен `1`.
- Одинаковое начало и окончание считается ошибкой. Поддерживается длительность от 1 до 1439 минут.

С этапа 8 правила формата и допустимого интервала находятся в `shared/src/shift-time.ts`. Форма определяет переход через полночь по порядку часов через `createShiftTime`; клиентское хранилище и сервер используют общий `isValidShiftTime`. API по-прежнему требует явного `endDayOffset` и отклоняет флаг, не соответствующий времени. Пустые часы и секунды не допускаются.

В макете шаблон «Вечер» со временем `15:00–23:00` подписан как 9 часов. В модели сохраняются указанные часы, длительность вычисляется из времени и составляет 8 часов.

## Сущности

| Модель | Назначение |
| --- | --- |
| `Employee` | ФИО, должность, необязательный аватар, порядок строк |
| `ShiftTemplate` | Код, название, время, переход через полночь, цвет, порядок шаблонов |
| `Schedule` | Ревизия общего расписания и часовой пояс |
| `ShiftAssignment` | Сотрудник, календарная дата, снимок времени и цвета, необязательная ссылка на шаблон |
| `SchedulePublication` | Версия опубликованного расписания, время публикации, полный JSON-снимок |
| `ScheduleRequest` | Результат завершённой операции сохранения или публикации для повторов запроса |

Одна пара сотрудник–дата содержит одну смену. Внешние ключи связывают назначения с сотрудниками и расписанием. Удаление используемого шаблона обнуляет `templateId`, сохранённые часы и цвет остаются свойствами назначения. Удаление сотрудника с назначениями ограничено внешним ключом.

Публикация хранит снимок версии `schemaVersion: 1` с сотрудниками, шаблонами, назначениями, часовым поясом и ревизией. Дальнейшие изменения справочников и рабочего расписания сохраняют содержимое ранее опубликованного снимка.

Демозаполнение добавляет восемь сотрудников и три шаблона с постоянными идентификаторами. Сотрудники получают собственные абстрактные SVG-аватары `/avatars/employee-1.svg` … `/avatars/employee-8.svg`. Повторный запуск добавляет отсутствующие записи, сохраняет отредактированные поля, назначения, ревизии и публикации. Только у восьми демонстрационных сотрудников пустой аватар или соответствующий старый `/avatars/employee-N.png` заменяется на SVG; пользовательские URL сохраняются.

## Чтение

| Метод и путь | Успешный ответ |
| --- | --- |
| `GET /api/employees` | `EmployeesResponse`, сотрудники упорядочены по `sortOrder`, затем `id` |
| `GET /api/shift-templates` | `ShiftTemplatesResponse`, шаблоны упорядочены по `sortOrder`, затем `id` |
| `GET /api/schedule?from=2026-11-01&to=2026-11-30` | `ScheduleResponse`, границы периода включены |

Расписание возвращает `from`, `to`, общую `revision`, `timeZone`, назначения за период и `latestPublication`. До первой публикации `latestPublication` равно `null`. Метаданные и назначения читаются из согласованного снимка БД.

Назначения отсортированы по дате, затем идентификатору сотрудника. Отсутствие назначения представлено отсутствием записи в массиве. Покрытие рассчитывается клиентом из всех назначений за дату, включая строки, скрытые поиском.

## Изменение расписания

`POST /api/schedule/changes` принимает `SaveScheduleRequest`.

```json
{
  "requestId": "30000000-0000-4000-8000-000000000001",
  "baseRevision": 0,
  "changes": [
    {
      "type": "assign-template",
      "cell": {
        "employeeId": "10000000-0000-4000-8000-000000000001",
        "date": "2026-11-19"
      },
      "templateId": "20000000-0000-4000-8000-000000000001"
    }
  ]
}
```

| Тип изменения | Параметры и поведение |
| --- | --- |
| `assign-template` | `cell`, `templateId`. Скопировать время и цвет шаблона в ячейку, заменив существующую смену |
| `assign-custom` | `cell`, `time` с `startTime`, `endTime`, `endDayOffset`. Назначить собственные часы, `templateId` становится `null`, используется цвет собственной смены из макета |
| `delete` | `cell`. Очистить назначение. Повторная очистка пустой ячейки допустима |
| `move` | `from`, `to`, `replaceExisting`. Перенести снимок смены, сохранив идентификатор назначения, часы и цвет. При занятой цели замена разрешена только с `replaceExisting: true` |

Массовое назначение передаёт одно изменение на каждую выбранную ячейку. Один запрос содержит до 1000 изменений, размер JSON-тела ограничен 1 МБ. Неизвестные поля и несовпадающие типы значений отклоняются. Изменения применяются последовательно в порядке массива внутри одной транзакции. Пустой источник переноса и перенос в ту же ячейку считаются ошибкой. При любой ошибке пакет полностью откатывается.

Успех возвращает HTTP 200 и `SaveScheduleResponse` с `requestId`, актуальной `revision`, итоговыми назначениями затронутых ячеек и `deletedCells`. Массивы отражают конечное состояние пакета. Ячейка присутствует в одном из них, даже если менялась несколько раз.

Любой пакет с непустым `changes` увеличивает ревизию ровно один раз. Запрос с пустым массивом допустим и сохраняет текущую ревизию после её проверки.

## Повторы и одновременные изменения

- Клиент генерирует `requestId` для конкретного сохранения и сохраняет его при повторе после сетевого сбоя.
- Сервер сначала ищет завершённый запрос с этим идентификатором. Для того же маршрута и содержимого возвращает сохранённый ответ, даже если текущая ревизия уже увеличилась.
- Отпечаток запроса — SHA-256 канонического JSON проверенного тела с упорядоченными ключами объектов и сохранённым порядком элементов массивов. UUID приводятся к нижнему регистру. Тип операции `save` или `publish` проверяется отдельно.
- Использование того же `requestId` с другим телом или маршрутом возвращает `REQUEST_ID_REUSED`.
- Для нового запроса сервер блокирует запись общего расписания до конца транзакции. После получения блокировки повторно проверяет `requestId`, затем `baseRevision`. Так одновременно пришедшие повторы получают один результат. Устаревшая ревизия возвращает `REVISION_CONFLICT` и `currentRevision`.
- Изменения, новая ревизия, публикация и запись успешного результата фиксируются одной транзакцией. Ошибочные запросы оставляют данные в исходном состоянии.

## Публикация

На этапе 10 эта семантика подключена к интерфейсу: публикация сохраняет правки и создаёт независимый снимок всего расписания.

`POST /api/schedule/publish` принимает `PublishScheduleRequest` с теми же полями, что и сохранение. Сервер применяет изменения, увеличивает ревизию один раз, создаёт снимок всего расписания и возвращает `PublishScheduleResponse`.

Даже при пустом массиве изменений публикация создаёт новую версию. Повтор того же запроса возвращает уже созданную публикацию. Поле `publication` содержит `id`, `revision`, `publishedAt`. Операция сохранения возвращает изменённые назначения, операция публикации дополнительно сохраняет полный снимок в БД.

## Поведение клиента при сохранении

Клиент отправляет конечную разницу по всему загруженному черновику. Простые переносы в освобождённую ячейку используют `move`, остальные изменения представляются итоговыми назначениями и удалениями. Сложная перестановка может получить новые серверные идентификаторы; итоговые часы, шаблоны и ячейки сверяются по содержимому, не по локальным ID.

После ответа проверяются `requestId`, ожидаемая ревизия и полное покрытие затронутых ячеек без повторов. При неизвестном результате — сетевой ошибке, 5xx или некорректном ответе — сохраняется исходный запрос и блокируются новые правки до его повтора. После 409 сравнение версий выполняется отдельно; оно не записывает данные. Решения пользователя обновляют базу и черновик, последующий POST снова проверяет ревизию на сервере.

Для проверочного сервера на 1000 сотрудников `ScheduleResponse` может содержать `readOnly: true`. Это признак локального демо: назначения редактируются в памяти, кнопки записи отключены. Основной Express API этот признак не выставляет, а тестовый сервер принимает только GET.

## Ошибки API

Все ошибки API расписания используют `ApiErrorResponse` с объектом `error` и полями `code`, `message`, необязательными `details` и `currentRevision`.

| HTTP | Код | Ситуация |
| --- | --- | --- |
| 400 | `VALIDATION_ERROR` | Некорректный JSON, идентификатор, дата, время или структура пакета |
| 404 | `NOT_FOUND` | Указанный сотрудник, шаблон или источник переноса отсутствует |
| 409 | `REVISION_CONFLICT` | Расписание изменилось после загрузки клиентом |
| 409 | `REQUEST_ID_REUSED` | Идентификатор успешного запроса использован для другой операции |
| 409 | `CELL_OCCUPIED` | Перенос в занятую ячейку без подтверждённой замены |
| 413 | `VALIDATION_ERROR` | Размер JSON-тела превышает 1 МБ |
| 500 | `INTERNAL_ERROR` | Неожиданная серверная ошибка |

Внутренние сообщения PostgreSQL и Prisma сохраняются в серверном журнале. Клиент получает сообщение и код, пригодные для отображения и обработки.
